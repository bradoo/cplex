# CPLEX 上午学习复习笔记

这份文档整理今天上午学到的 CPLEX 项目落地方法。下午复习时，可以先看每一节的“核心句”，再回看例子。

## 1. 接入真实业务数据

核心句：

```text
优化模型 = 业务数据 + 决策逻辑
```

真实项目里，模型不能长期依赖手写样例数据，而要从 Excel、CSV、数据库或业务系统读取：

- 订单数据：市场、SKU、数量、平台、承诺时效
- 库存数据：仓库、SKU、当前库存、可用库存
- 物流数据：线路、成本、时效、容量、清关方式
- 供应商数据：报价、起订量、产能、交期、可靠性
- 财务数据：预算、现金流、仓储费、缺货损失

落地流程：

```text
读取数据 -> 清洗数据 -> 建变量/目标/约束 -> 求解 -> 导出结果
```

业务判断句：

```text
CPLEX 项目真正落地时，难点往往不是求解器，而是把业务数据整理成模型能理解的变量、目标和约束。
```

## 2. 设计优化模型的数据表结构

好的数据表通常分成四类：

```text
对象表：有哪些东西
参数表：这些东西有什么属性
关系表：对象之间怎么连接
场景表：这次求解用什么假设
```

例子：

- 对象表：仓库、SKU、市场、供应商、订单组
- 参数表：仓容、毛利、成本、提前期、风险评分
- 关系表：仓库-市场、供应商-SKU、仓库-仓库、SKU-平台
- 场景表：需求倍率、SLA、预算、罚分、政策假设

不要把所有信息塞进一张大表。一张大表短期简单，长期会让模型难以扩展。

业务判断句：

```text
优化模型的数据表不是为了好看，而是为了让变量、目标和约束能稳定、清楚、可扩展地被生成。
```

## 3. 从 Excel / CSV 自动生成变量和约束

核心句：

```text
表里的行，决定变量的索引范围；
表里的字段，决定目标函数和约束参数。
```

例如线路表：

```text
warehouse_id,market,ship_cost,lead_time_days,capacity
LA_3PL,US_West,3.2,2,5000
NJ_3PL,US_East,3.4,2,4500
Rotterdam,EU,4.1,3,4000
```

可以自动生成变量：

```text
ship[warehouse,market]
```

这样以后新增线路，只需要在表里加一行，不需要重写模型代码。

业务判断句：

```text
一个可落地的 CPLEX 模型，不应该把业务对象写死在代码里，而应该让业务数据驱动变量、目标和约束。
```

## 4. 数据校验

数据进入模型前，要做三层校验。

字段校验：

```text
字段是否存在，类型是否正确，是否为空。
```

范围校验：

```text
容量 > 0
需求 >= 0
成本 > 0
可靠性在 0 到 1 之间
折扣率在 0 到 1 之间
```

关系校验：

```text
有需求的市场必须有可用线路；
每个 SKU 至少有可采购供应商；
调拨线路里的 from/to 仓库必须存在；
订单组的截止波次必须存在。
```

业务判断句：

```text
优化模型上线前，数据校验和模型本身一样重要；它决定了模型输出是可信建议，还是漂亮但危险的数字。
```

## 5. 无解诊断

模型无解不代表 CPLEX 错了，而是说明：

```text
当前数据和约束下，没有任何方案能同时满足所有规则。
```

常见无解来源：

- 总量冲突：总需求超过总供应或总容量
- 局部冲突：总量够，但某个市场、仓库、SKU 或技能局部不够
- 规则冲突：规则单独看合理，放在一起互相打架
- 参数过紧：SLA、可靠性、预算等要求超过当前能力

解释无解时，不要只说 `infeasible`，要说明：

```text
冲突类型
涉及对象
冲突原因
修复建议
```

业务判断句：

```text
无解不是失败，而是模型帮我们发现业务规则之间存在无法同时满足的冲突。
```

## 6. 把硬约束改成软约束

硬约束：

```text
必须满足，不满足就无解。
```

软约束：

```text
尽量满足，实在满足不了可以违反，但要付出代价。
```

典型做法：

```text
硬约束：发货量 = 市场需求

软约束：发货量 + 未履约量 = 市场需求
目标函数加入：未履约量 × 未履约罚分
```

可软化的规则：

- 需求满足
- SLA 延期
- 库存目标
- 员工偏好
- 服务水平

不应轻易软化的规则：

- 法律合规
- 安全红线
- 财务硬限制

业务判断句：

```text
软约束不是让模型随便违反规则，而是把“违反规则的业务代价”显式写进目标函数，让模型选择最小损失方案。
```

## 7. 校准罚分权重

罚分权重本质上是业务损失估值。

例子：

```text
未履约罚分 = 10，扩容成本 = 18
模型可能选择丢单。

未履约罚分 = 50，扩容成本 = 18
模型更可能选择扩容。
```

未履约罚分可以包含：

- 订单毛利损失
- 平台绩效扣分
- 客户差评风险
- 补偿成本
- 未来复购损失
- 品牌体验损失

校准方法：

```text
罚分 = 10、30、50、100 分别求解，
观察模型从接受缺口切换到扩容/加班/加急的临界点。
```

业务判断句：

```text
校准罚分的目的，不是调出一个“好看结果”，而是让模型的取舍和业务真实损失保持一致。
```

## 8. 敏感性分析

敏感性分析回答：

```text
当关键参数变化时，最优决策什么时候改变？
```

常见分析参数：

- 需求倍率
- 未履约罚分
- SLA 天数
- 空运容量
- 海运提前期
- 促销预算
- 关税税率
- 碳价

输出重点不是一堆结果，而是找到决策边界：

```text
扩容触发点
缺口消失点
边际收益放缓点
路线切换点
```

业务判断句：

```text
敏感性分析的价值，不是多算几个结果，而是找到业务策略从一种选择切换到另一种选择的边界。
```

## 9. 图表和管理层看板

模型结果要用图表翻译给业务方。

常用图表：

- 折线图：看趋势，例如预算增加后净贡献变化
- 柱状图：看对比，例如不同方案成本对比
- 堆叠图：看结构，例如成本构成、物流路径构成
- 阈值标记：看决策边界，例如什么时候开始扩容

管理层看板建议顺序：

```text
先看结果：总成本、缺口、SLA、净贡献
再看原因：成本构成、订单流向、瓶颈资源
最后看边界：参数变化到哪里方案会切换
```

业务判断句：

```text
好的优化看板不是展示所有数字，而是突出趋势、结构和决策边界。
```

## 10. 把 CPLEX 模型包装成 API

真实落地时，业务系统不应该直接运行 Python 脚本，而应该调用 API。

流程：

```text
前端 / ERP / WMS / OMS
-> POST /api/solve
-> 读取参数
-> 构建模型
-> 调用 CPLEX
-> 整理结果
-> 返回 JSON
```

API 设计重点：

- 输入要用业务语言，不要暴露内部变量名
- 输出要可解释，不只返回 objective value
- 错误要友好，尤其是无解和参数错误
- 要设置 time_limit 和 mip_gap
- 要做数据校验

业务判断句：

```text
当 CPLEX 模型变成 API 后，它就不再只是分析工具，而是可以被前端、ERP、WMS、OMS 自动调用的决策服务。
```

## 11. 自动化测试

优化模型也需要测试，尤其是 API 化之后。

测试类型：

- 健康检查测试：服务是否活着
- 默认场景测试：主流程是否正常返回
- 输入校验测试：脏数据是否被拦截
- 无解/软约束测试：异常场景是否可解释
- 回归测试：关键业务结果是否被意外破坏

未来跨境电商模拟器可以测试：

```text
所有 35 个 scenario 都能返回 200；
每个 scenario 都有 status；
未知 scenario 返回友好错误；
关键场景的核心字段稳定存在。
```

业务判断句：

```text
当 CPLEX 模型要进入业务系统时，自动化测试就是防止“模型悄悄变坏”的安全网。
```

## 12. 实验记录

每次求解最好记录：

- 模型版本：model_name、script_name、git_commit
- 输入参数：scenario、需求倍率、罚分、SLA、预算
- 求解参数：time_limit、mip_gap、状态、求解时间
- 业务结果：总成本、缺口、扩容、供应商、路线、净贡献
- 备注标签：experiment_name、owner、created_at、notes

常用格式：

```text
JSONL：适合程序追加，每行一条实验记录
CSV：适合 Excel 打开和管理层对比
```

业务判断句：

```text
实验记录把每次优化从一次性答案，变成可以复盘、比较和审计的决策历史。
```

## 13. 模型版本管理

一次优化结果由三类版本共同决定：

```text
代码版本：Git commit
业务规则版本：罚分、SLA、评分阈值、碳价等规则配置
数据版本：订单快照、库存快照、运价版本、供应商评分版本
```

完整记录示例：

```json
{
  "model_name": "cross_border_capacity_expansion",
  "git_commit": "c605f3d",
  "ruleset": "peak_season_2026_v1",
  "orders_snapshot": "2026-08-27_10:00",
  "inventory_snapshot": "2026-08-27_10:00",
  "solver_status": "optimal"
}
```

业务判断句：

```text
模型版本管理的目的，是让每一次优化建议都能说清楚：谁算的、用哪版规则算的、基于哪批数据算的。
```

## 14. 把结果转成业务行动清单

CPLEX 输出的是变量值，但业务方需要行动。

例如：

```text
extra_capacity[Rotterdam] = 500
```

应该翻译成：

```text
行动：给 Rotterdam EU Hub 购买 500 单临时履约容量
负责人：欧洲仓运营负责人
截止时间：本周五前
原因：扩容成本低于未履约损失
预期效果：EU 未履约订单从 500 降到 0
```

行动清单字段：

```text
action_type
target
quantity
owner
deadline
reason
impact
risk
priority
```

业务判断句：

```text
优化项目能不能落地，不取决于 objective value 多漂亮，而取决于结果能不能变成清楚、可执行、可追踪的行动清单。
```

## 15. 给优化建议加解释理由

业务方会问：

```text
为什么是这个方案？
为什么不是那个方案？
为什么这个仓要扩容？
为什么最低价供应商没被选？
```

解释理由可以分四类：

- 成本解释：为什么这个方案更划算
- 约束解释：为什么某些方案不能选
- 风险解释：为什么避开便宜但高风险方案
- 机会成本解释：选择 A 意味着放弃 B

解释模板：

```text
模型建议：[行动]
原因 1：[成本或收益优势]
原因 2：[满足关键约束]
原因 3：[降低风险或避免损失]
未选择替代方案的原因：[替代方案被什么卡住]
预期影响：[成本下降、缺口减少、SLA 提升、净贡献增加]
```

业务判断句：

```text
业务方愿不愿意相信优化结果，往往不取决于模型多复杂，而取决于结果解释是否讲清了成本、约束、风险和机会成本。
```

## 16. 完整 CPLEX 项目落地流程

完整流程：

```text
业务问题
-> 变量
-> 目标
-> 约束
-> 数据
-> 求解
-> 解释
-> 行动
-> 上线
```

上线前要准备：

- API 服务
- 自动化测试
- 数据校验
- 实验记录
- 模型版本管理
- 结果报表
- 权限和审批流程
- 监控与告警

业务判断句：

```text
一个成功的 CPLEX 项目，不是写出一个能求解的模型，而是建立一套从业务问题到可执行行动、可解释结果、可持续运行的决策流程。
```

## 17. 判断业务问题是否适合 CPLEX

适合 CPLEX 的问题通常有五个特点：

```text
有明确决策：选哪个、分多少、排到哪里
有可量化目标：成本、利润、缺口、风险、服务水平
有明确约束：预算、容量、SLA、库存、技能
组合很多：人工很难穷举
需要可执行方案：采购、调拨、排班、开仓、分配
```

工具分工：

```text
BI / 报表：发生了什么
机器学习：可能会发生什么
规则引擎：满足条件就执行什么
CPLEX：在限制条件下应该怎么做最好
```

业务判断句：

```text
CPLEX 不是万能工具，它最适合把复杂约束下的多方案取舍，转成可执行的最优决策。
```

## 18. 机器学习 + CPLEX

分工：

```text
机器学习告诉我们“可能会发生什么”；
CPLEX 决定“应该怎么做最好”。
```

常见组合：

- 需求预测 + 补货优化
- 销量预测 + 促销优化
- 退货率预测 + 逆向物流优化
- 风险预测 + 物流韧性优化
- 工单预测 + 客服排班优化

关键理解：

```text
预测模型的输出，往往正是优化模型的输入。
```

业务判断句：

```text
机器学习解决“未来可能怎样”，CPLEX 解决“面对这个未来，我们现在应该怎么做”。
```

## 19. 场景优化和稳健优化

预测一定有误差，所以不能只按一个预测值做决策。

场景优化：

```text
低需求 / 中需求 / 高需求
按概率计算期望成本
```

稳健优化：

```text
关注坏情况发生时也不要损失太大。
```

对比：

```text
普通最优：当前预测下成本最低
场景优化：多个未来下期望成本最低
稳健优化：坏情况发生时也能接受
```

业务判断句：

```text
场景优化和稳健优化，是把预测误差从“事后解释”提前变成“事前决策约束”。
```
