# CPLEX 下午学习复习笔记

这份文档整理今天下午学到的内容，重点是：如何把 CPLEX 从“模型会算”推进到“业务能用、管理层能看懂、项目能展示”。

## 1. 候选方案比较

核心句：

```text
优化模型不一定只输出一个答案，也可以帮助业务方比较不同策略偏好的成本、服务和风险取舍。
```

真实管理决策里，经常需要多个候选方案：

```text
精益方案：成本最低，但风险较高
平衡方案：成本中等，服务和风险可控
稳健方案：成本最高，但高需求或异常情况下更安全
```

比较候选方案时，不要只看总成本。至少要看：

- 总成本
- 未履约订单
- SLA 达成率
- 库存剩余或积压
- 风险订单量
- 执行复杂度

常见生成候选方案的方法：

- 调整目标权重，例如成本权重、风险权重、SLA 权重
- 设置不同约束，例如是否要求备份能力
- 固定部分决策，例如必须启用或禁止某个仓
- 使用 solution pool 找多个接近最优的可行解

业务判断句：

```text
候选方案比较的价值，是把“哪个方案最好”变成“在什么管理偏好下，哪个方案最合适”。
```

## 2. 业务指标体系

核心句：

```text
模型目标函数负责“算最优”，业务指标体系负责“解释结果、比较方案、推动复盘”。
```

`objective_value` 适合求解器，但不一定适合管理层复盘。要把结果拆成业务指标。

五类核心指标：

**成本指标**

- 总成本
- 仓库固定成本
- 运输成本
- 临时扩容成本
- 库存持有成本
- 缺货罚分
- 关税和清关成本

**服务指标**

- SLA 达成率
- 平均送达天数
- P90 / P95 送达天数
- 未履约订单
- 延期订单
- 订单准时出库率

**库存指标**

- 期末库存
- 库存周转天数
- 安全库存覆盖率
- 缺货量
- 积压库存
- 跨仓调拨量

**风险指标**

- 高风险线路订单量
- 单一供应商占比
- 天气风险暴露
- 故障场景缺口
- 备用能力覆盖率

**执行指标**

- 新仓启用数量
- 调拨线路数
- 供应商下单数
- 加班波次数
- 审批动作数
- 行动清单完成率

业务判断句：

```text
CPLEX 项目要进入管理复盘，不能只交 objective value，而要交一套能解释成本、服务、库存、风险和执行变化的指标体系。
```

## 3. 接入日报和周报

核心句：

```text
CPLEX 结果进入日报/周报后，优化就不再是一次性分析，而是持续运营的一部分。
```

日报适合看短期风险和动作：

- 今日缺货风险 SKU
- 今日建议调拨
- 今日履约缺口
- 今日 SLA 风险仓库
- 今日需要加班的订单波次

周报适合看趋势和复盘：

- 本周总成本变化
- 本周未履约订单变化
- 本周库存覆盖变化
- 本周供应商风险变化
- 本周候选方案对比
- 下周建议行动清单

输出建议用三层结构：

```text
指标：发生了什么
解释：为什么发生
行动：建议做什么
```

业务判断句：

```text
优化模型真正产生长期价值，是当它能持续发现问题、解释原因、提出行动，并在复盘中验证效果。
```

## 4. 审批和人工干预机制

核心句：

```text
CPLEX 给建议，业务做决策；审批和人工干预机制负责把模型建议变成可控、可追踪、可复盘的运营动作。
```

模型建议不能全部自动执行，要按风险分层。

**自动执行**

适合低金额、低风险、可逆、频率高的动作：

- 小批量跨仓调拨
- 低价值 SKU 补货提醒
- 订单波次内部调整
- 客服班次微调

**人工确认**

适合中等金额、中等风险、需要运营判断的动作：

- 临时扩容
- 加急空运
- 供应商分单调整
- 促销预算调整
- 清仓折扣调整

**管理层审批**

适合高金额、高风险、不可逆或战略影响大的动作：

- 启用新海外仓
- 大额采购
- 大规模清仓
- 切换主物流服务商
- 突破预算上限
- 改变 SLA 承诺

人工干预方式：

- 锁定决策：某动作必须发生
- 禁止决策：某动作不能发生
- 调整参数：改变罚分、风险容忍度、SLA 权重等

业务判断句：

```text
优化系统上线后，最好的状态不是完全无人干预，而是让人工干预有记录、有理由，并反过来帮助模型持续变准。
```

## 5. 用人工干预反向改进模型

核心句：

```text
人工干预不是噪音，而是模型学习真实业务规则的重要反馈数据。
```

如果业务方经常修改或拒绝模型建议，通常说明模型没有完全表达真实业务。

需要重点分析：

**经常被拒绝的动作**

可能说明：

- 数据不准
- 成本没有算全
- 有隐藏约束
- 执行上不可行
- 业务偏好没有写进模型

**经常被修改的数量**

可能说明：

- 实际容量比模型低
- 可用库存口径不对
- 仓库人手不足
- 操作窗口约束缺失

**经常被锁定的动作**

说明这些动作可能应该进入模型约束，例如：

- 核心供应商最低采购量
- 重点平台最低供货比例
- 重点市场必须有本地履约能力

关键指标：

```text
建议采纳率 = 直接采纳建议数 / 总建议数
```

还可以看：

- 修改幅度
- 拒绝原因分布
- 干预后效果
- 重复干预对象

业务判断句：

```text
成熟的优化系统，不是追求业务永远不改模型建议，而是能从每一次人工修改里学习哪些规则还没写进模型。
```

## 6. ROI 评估

核心句：

```text
CPLEX 项目的 ROI 来自成本节省、损失减少、毛利提升、人效提升和风险降低，而不只是目标函数下降。
```

五类收益：

**成本节省**

```text
成本节省 = 原方案成本 - 优化方案成本
```

例如运输成本、仓储成本、采购成本、加班成本下降。

**损失减少**

```text
损失减少 = 原方案损失金额 - 优化方案损失金额
```

例如未履约、延期、缺货、平台扣分、退货损失下降。

**收入或毛利提升**

```text
毛利提升 = 优化后毛利 - 原方案毛利
```

例如库存优先分给高毛利渠道，促销预算投给更值得的 SKU。

**人效提升**

```text
人效收益 = 节省工时 × 人力成本
```

例如排班、补货、调拨和周报从人工 Excel 改成自动建议。

**风险降低**

```text
风险收益 = 风险事件概率 × 事件损失下降
```

例如降低单一供应商依赖、天气风险暴露和故障场景缺口。

ROI 公式：

```text
年度收益 = 成本节省 + 损失减少 + 毛利提升 + 人效收益 + 风险收益
ROI = (年度收益 - 年度成本) / 年度成本
```

业务判断句：

```text
优化项目要获得管理层支持，不能只证明模型会算，而要证明它持续带来了可衡量的经营改善。
```

## 7. 试点方案设计

核心句：

```text
优化项目最好的起步方式，是选一个边界清晰、数据可得、价值可衡量的场景，用小试点建立业务信任。
```

好的试点场景通常具备：

- 痛点明显
- 数据相对容易拿到
- 决策频率高
- 结果容易衡量
- 影响范围可控
- 业务负责人愿意配合

适合试点的跨境电商场景：

- 跨仓库存调拨
- 旺季临时扩容
- 供应商采购分配
- 促销预算计划
- 客服排班
- 订单波次排程

试点步骤：

```text
1. 选择高价值但边界清晰的场景
2. 定义试点范围
3. 定义成功指标
4. 准备数据和历史基线
5. 并行运行，不急着自动执行
6. 记录采纳、修改和拒绝原因
7. 复盘试点结果
```

试点结论通常有三种：

```text
扩大试点
继续迭代
暂停推进
```

## 8. 从试点扩展到正式上线

核心句：

```text
试点证明模型有价值，正式上线要证明模型能稳定、可解释、可审计地进入业务流程。
```

正式上线要扩展 6 个方向：

**数据接入自动化**

接入 OMS、WMS、TMS、ERP、客服系统、广告平台等数据源。

**模型服务化**

支持：

- 同步求解
- 异步求解
- 批量求解
- 定时求解
- 结果查询
- 历史记录

**结果产品化**

输出：

- 指标看板
- 行动清单
- 异常提醒
- 解释理由
- 候选方案对比
- 审批状态
- 执行追踪

**流程闭环**

```text
模型建议 -> 业务审批 -> 执行落地 -> 结果反馈 -> 指标复盘 -> 模型迭代
```

**多场景复用**

沉淀数据读取、校验、场景配置、求解参数、结果解释、行动清单和实验记录能力。

**治理和运维**

包括模型版本、数据版本、规则版本、权限、监控、审计、回滚。

业务判断句：

```text
CPLEX 项目从试点走向上线，关键不是把模型做大，而是把数据、服务、解释、审批、执行和复盘连成闭环。
```

## 9. 可复用的优化平台架构

核心句：

```text
企业级 CPLEX 能力不是一堆孤立模型，而是一套能持续接入数据、运行模型、解释结果、推动行动并复盘效果的决策优化平台。
```

平台可以分成 8 层：

```text
1. 数据接入层
2. 数据校验层
3. 场景配置层
4. 模型层
5. 求解服务层
6. 结果解释层
7. 流程协同层
8. 治理和监控层
```

整体链路：

```text
业务系统数据
-> 数据校验
-> 场景配置
-> 模型构建
-> 求解服务
-> 结果解释
-> 审批执行
-> 复盘治理
```

轻量版平台可以从这些能力开始：

- CSV / Excel 输入
- Flask API
- JSONL 实验记录
- Markdown / HTML 报告
- 简单 Web 页面
- 人工审批
- Git 做模型版本管理

## 10. 角色分工和协作流程

核心句：

```text
CPLEX 项目是跨部门决策工程，不只是算法开发。
```

常见角色：

- 业务负责人：定义问题、目标和约束
- 数据负责人：确认数据来源、字段口径和更新频率
- 优化建模负责人：设计变量、目标、约束和求解策略
- 工程负责人：API、数据管道、任务调度、测试和监控
- 产品/前端负责人：页面、图表、行动清单和交互体验
- 审批和执行负责人：确认建议并推动落地
- 管理层 Sponsor：确认优先级、资源和跨部门协同

协作流程：

```text
业务提出问题
-> 数据确认口径
-> 建模设计规则
-> 业务确认约束和罚分
-> 工程接入系统
-> 产品设计页面
-> 试点验证结果
-> 审批执行建议
-> 管理层复盘 ROI
-> 模型持续迭代
```

业务判断句：

```text
优化项目成功的关键，不是某个人把模型写出来，而是业务、数据、建模、工程和管理层围绕同一套目标与约束形成协作闭环。
```

## 11. 管理层汇报方法

核心句：

```text
管理层不需要先理解 CPLEX 的数学细节，而需要理解它能把复杂业务取舍变成可比较、可解释、可执行的方案。
```

汇报结构建议：

```text
1. 背景：为什么要做
2. 问题：当前决策难在哪里
3. 方法：CPLEX 做什么
4. 成果：已经做出了什么
5. 价值：能带来什么改善
6. 风险和边界：哪些还需要补
7. 请求：希望管理层支持什么
```

汇报时少讲数学细节，多讲：

- 业务痛点
- 决策复杂性
- 可运行成果
- 指标改善
- 试点计划
- 需要管理层支持的资源

业务判断句：

```text
一次好的 CPLEX 管理层汇报，不是证明模型高级，而是证明业务问题重要、优化方法可行、收益可以衡量、下一步试点清楚。
```

## 12. 个人能力地图和项目作品集

核心句：

```text
学习成果不只是知识点，而是可以整理成能力地图、项目作品和业务表达。
```

个人能力地图可以分成 6 个模块：

- 数学优化建模能力
- 业务建模能力
- 数据建模能力
- 工程化能力
- 结果解释能力
- 项目落地能力

项目作品集可以分成：

- 基础模型作品：背包、运输、仓库选址
- 排班系统作品：排班求解器、Web/API、软约束、多目标、测试
- 跨境电商模拟器作品：35 个业务场景
- 分享材料作品：PPT、课件、经理演示脚本
- 复习材料作品：上午和下午复习笔记

对外介绍可以这样说：

```text
我基于 IBM CPLEX / DOcplex 构建了一套优化建模学习项目，
从背包、运输、仓库选址等基础模型开始，
逐步扩展到员工排班系统和跨境电商库存物流模拟器。
项目覆盖软约束、多目标优化、敏感性分析、API 化、自动化测试、
实验记录、模型解释和管理层汇报材料。
```

## 13. 作品集 README

核心句：

```text
作品集 README 不是文件目录，而是项目价值的导览图。
```

README 首页应该让别人 3 分钟内看懂：

- 这个项目是什么
- 解决了什么问题
- 用了什么技术
- 有什么可运行成果
- 有什么业务价值
- 怎么快速体验

作品集版 README 结构：

```text
1. 项目一句话介绍
2. 项目亮点
3. 快速体验
4. 可运行应用
5. 核心业务场景
6. 技术栈
7. 文档入口
8. 学习路线
9. 能力总结
```

业务判断句：

```text
作品集版 README 的目标不是证明文件很多，而是让别人快速相信：这个项目能运行、能解释、能展示业务优化能力。
```
